# Supply-chain and license evidence

This document describes repeatable repository evidence. It does not grant a
license to third-party code and it does not replace legal review.

## Evidence generation

The weekly/manual **Supply-chain evidence** workflow archives:

- a CycloneDX source SBOM generated by the SHA-pinned Anchore action;
- `cargo metadata --locked` for the shared format core;
- Gradle's default-core `releaseRuntimeClasspath` report. The format core and
  JNA are mandatory build inputs; there is no `nativeCore` property;
- hashes of the Gradle Wrapper, `Cargo.lock`, and key build inputs; and
- the observed Java/Rust/Gradle/runner versions.

The **Release candidate evidence** workflow adds the actual unsigned Android
candidate, SHA-256 manifest, Android test/lint reports, iOS XCTest `.xcresult`
bundle, native-core logs, a release-commit SBOM, and a GitHub provenance
attestation for the unsigned APK. The **Signed GitHub release** workflow uses
only administrator-provided credentials, rechecks artifacts, imports the iOS
certificate into a temporary keychain with the non-interactive `codesign` key
partition, emits signed APK/AAB/IPA checksums, and attests those exact assets
before an explicit publication step. Its build and signing jobs receive only
read-only repository access; the final publication job alone receives content
write and attestation/OIDC permissions.

SBOMs and dependency reports are inventory inputs, not automated proof of
license compatibility. Their scope must be checked against the final artifact:
native/system libraries, embedded assets, generated code, and store packaging
can differ from a source scan.

## Release license reconciliation

For every asset intended for distribution, the release owner must:

1. save the generated SBOM, Gradle report, Cargo metadata, release checksum
   manifest, and provenance link under the organization's evidence retention
   policy;
2. compare their components with `THIRD_PARTY_NOTICES.md`, add exact versions,
   source URLs, full license/NOTICE texts, and every applicable attribution,
   including the Readium BSD-3-Clause text and the actual PDFium/MobileVLCKit
   materials delivered in the final artifact;
3. confirm whether each library is static, dynamic, system-provided, or
   embedded in the APK/AAB/IPA; and
4. obtain legal approval for copyleft, source-offer, relinking, patent, codec,
   UnRAR, Apple-distribution, and store obligations before publication.

Do not edit field names, add JSON aliases, or introduce protocol compatibility
mappings while doing this work. Supply-chain metadata is separate from the
strict BookOrbit and Wi-Fi contracts.

## Secret handling

All signing and Apple credentials belong in the protected `production`
environment documented in [`RELEASING.md`](../RELEASING.md). The workflows
write decoded credentials under the runner temporary directory, except for the
provisioning profile that Xcode requires temporarily under
`$HOME/Library/MobileDevice/Provisioning Profiles`; they delete each exact file
and the temporary keychain at job exit and never upload them as artifacts.
GitHub log redaction is not a substitute for avoiding `echo`, shell tracing,
diagnostic archives, or checked-in credential files.
